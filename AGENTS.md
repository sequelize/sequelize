# AGENTS.md

This file provides guidance to AI coding agents working with this repository. It is the only agent instruction file in the repository; keep agent guidance here rather than adding tool-specific copies.

## Project map

- Sequelize is a Yarn / Lerna monorepo for the ORM core and its dialect packages.
- `packages/core` contains the shared ORM implementation and most cross-dialect tests.
- `packages/{postgres,mysql,mariadb,sqlite3,mssql,db2,ibmi,oracle,snowflake}` contain dialect-specific connectors and behavior.
- `packages/utils`, `packages/validator-js`, and `packages/cli` are separate published packages with their own build and test scripts.
- Edit source under `packages/*/src`; `packages/*/lib` is generated by the build and should not be hand-edited.
- `build-packages.mjs` is the package build entry point; package scripts call it through `yarn build` / `lerna run build`.

## Architecture

- `packages/core` is dialect-agnostic. Dialect packages extend the abstract classes in `packages/core/src/abstract-dialect` (`dialect.ts`, the query generator, the query interface, `query.ts`, and `connection-manager.ts`).
- Each dialect package mirrors that layout in `packages/<dialect>/src`: `dialect.ts` declares feature support flags, `query-generator.js` generates SQL, `query-interface.js` or `query-interface.ts` implements schema operations, `query.js` executes queries and maps results, and `connection-manager.ts` wraps the driver.
- The codebase is migrating from JavaScript to TypeScript. Legacy `.js` classes extend a TypeScript counterpart (`Model extends ModelTypeScript`, `AbstractQueryGenerator extends AbstractQueryGeneratorTypeScript`) and ship a co-located `.d.ts`. Add new methods to the TypeScript class (`*-typescript.ts` or `*.internal.ts`) rather than the legacy `.js` file, and write all new files in TypeScript.
- Core files to know: `packages/core/src/model.js`, `packages/core/src/sequelize.js`, `packages/core/src/associations/`, `packages/core/src/data-types.ts`, and `packages/core/src/abstract-dialect/`.
- When changing query generation, update the abstract implementation in core and check every dialect override.
- `@sequelize/utils` provides shared utilities used across packages.
- Packages publish dual CommonJS/ESM builds through the `exports` field: `lib/` contains `.js`/`.d.ts` and `.mjs`/`.d.mts` outputs. `@sequelize/core/decorators-legacy` is a separate subpath export.
- `src/index.mjs` files are generated from `src/index.ts`. Run `yarn sync-exports` after changing a package's exports; `yarn test-exports` fails when they are out of sync.

## Branching and PRs

- Normal changes target `main`; the contribution guide only calls out `v6` as an exceptional target when agreed with maintainers.
- Bug fixes and new features must include an automated regression test that fails without the change.
- PR titles use the repository's conventional commit scheme: `docs`, `feat`, `fix`, or `meta`, optionally scoped to a package name (`fix(postgres): ...`).

## Build

- Use a CI-supported Node line: 20, 22, or 24. Prefer Node 24.
- Before installing, verify `node --version`; if it is not 20, 22, or 24, switch to a supported Node runtime before continuing.
- Do not assume newer Node versions work just because package metadata allows `>=24`; install pulls in native connector packages and untested runtimes can fail before the repo code builds.
- Use Yarn commands for dependency and workspace tasks; this repo is configured for Yarn 4 workspaces and patches.
- Run `yarn install --immutable` from the repository root, then `yarn build`.
- Tests import packages through their built `lib/` output. Rebuild after every source change or revision switch before running tests, or the tests will exercise stale code. `yarn build` is cached by Nx and is cheap when nothing changed; `node build-packages.mjs <package>` builds a single package.
- A working native addon toolchain is required because install builds packages such as `sqlite3`, `ibm_db`, `odbc`, and `oracledb`.
- On macOS, runtime tests that import `@sequelize/db2-ibmi` require a system `unixODBC` installation that provides `libodbc.2.dylib`.
- If Nx caching behaves unexpectedly, run `yarn nx reset`.

## Test

- The broad local checks are `yarn test:format`, `yarn test-typings`, and `yarn test-unit`.
- `yarn test-unit` starts with `test/esm-named-exports.test.js`, which imports every published package; missing native connector libraries can fail the suite before assertions run.
- The core test bootstrap in `packages/core/test/config/config.ts` imports every dialect package, so even SQLite-scoped core tests still need the runtime dependencies required by those imports.
- The documented baseline is `yarn lerna run test-sqlite3`.
- The lightest database-backed path is SQLite: `yarn lerna run test-integration-sqlite3 --scope=@sequelize/core`.
- For a single dialect, use the existing package scripts such as `yarn lerna run test-unit-postgres --scope=@sequelize/core` or `yarn lerna run test-integration-postgres --scope=@sequelize/core`.
- To run a single file, set `DIALECT` and pass the path to mocha from the package root: `cd packages/core && DIALECT=sqlite3 yarn mocha test/integration/utils.test.ts`.
- Non-SQLite integration tests require the corresponding database service; the repository provides `yarn start-<dialect>-oldest` and `yarn start-<dialect>-latest` helpers backed by Docker (definitions in `dev/<dialect>/{oldest,latest}`), `yarn stop-<dialect>` to stop them, and `yarn reset-<dialect>` to remove containers and volumes.
- CI runs against both the oldest and latest supported version of each database; test against both when touching dialect behavior.
- `yarn sscce-sqlite3` (or `yarn sscce-<dialect>`) is the quickest end-to-end smoke path after build and install.

## Testing conventions

- Keep regression tests in the package that owns the behavior: `packages/core/test` for ORM behavior, package-local tests for dialect or utility behavior.
- Use unit tests for pure logic and integration tests when the behavior depends on actual database semantics.
- Mocha picks up both `*.test.js` and `*.test.ts` under `packages/core/test/unit` and `packages/core/test/integration`. Write new tests in TypeScript.
- Integration tests import helpers from `packages/core/test/integration/support.ts`: `sequelize` (the shared instance for the current `DIALECT`), `beforeAll2` (runs setup once and returns its result to every test), and `setResetMode('drop' | 'truncate' | 'destroy' | 'none')`, which controls how the database is reset between tests. `drop` is the default; prefer a lighter mode when the suite allows it.
- Unit tests import from `packages/core/test/support.ts`; `expectsql` asserts generated SQL per dialect, and `getTestDialect()` returns the active dialect name.
- Chai assertions use the custom extensions declared in `packages/core/test/chai-extensions.d.ts`.
- Guard dialect-specific tests with `sequelize.dialect.supports.<feature>` or `sequelize.dialect.name`. Add new capability flags to `DialectSupports` in `packages/core/src/abstract-dialect/dialect.ts` and set them in each dialect's `dialect.ts` instead of hard-coding dialect names where possible.
- Dialect package unit tests live next to the source as `packages/<dialect>/src/*.test.ts` and run with `yarn lerna run test-unit --scope=@sequelize/<dialect>`.
- If a test command fails during setup, distinguish missing local prerequisites from code failures before changing source.

A minimal integration test for a new model feature:

```typescript
import type { CreationOptional, InferAttributes, InferCreationAttributes } from '@sequelize/core';
import { DataTypes, Model } from '@sequelize/core';
import { Attribute, NotNull } from '@sequelize/core/decorators-legacy';
import { expect } from 'chai';
import { beforeAll2, sequelize, setResetMode } from '../support';

describe('Model#newFeature', () => {
  if (!sequelize.dialect.supports.newFeature) {
    return;
  }

  setResetMode('destroy');

  const vars = beforeAll2(async () => {
    class User extends Model<InferAttributes<User>, InferCreationAttributes<User>> {
      declare id: CreationOptional<number>;

      @Attribute(DataTypes.INTEGER)
      @NotNull
      declare someField: number;
    }

    sequelize.addModels([User]);
    await sequelize.sync({ force: true });

    return { User };
  });

  beforeEach(async () => {
    await vars.User.create({ someField: 1 });
  });

  it('works', async () => {
    const user = await vars.User.findByPk(1, { rejectOnEmpty: true });
    await user.newFeature();
    expect(user.someField).to.equal(2);
  });
});
```

## Documentation and threat model

- Update documentation when a public API or user-visible behavior changes.
- `THREAT_MODEL.md` is a living security document; update it when a security-relevant trust boundary, documented invariant, or security-relevant default materially changes.

## Security analysis

- Read `THREAT_MODEL.md` before triaging or escalating any suspected vulnerability.
- Do not treat unusual behavior as a security issue unless you can identify a concrete attacker-controlled input, a reachable code path, and a plausible impact.
- Separate disposition from severity. Use the dispositions defined in `THREAT_MODEL.md` Appendix A verbatim and independently from impact level. That appendix is non-normative: present its output as a proposed rating and leave the final disposition and severity to maintainers.
- Before reporting a finding, check whether it is already covered by an existing issue, advisory, or documented behavior.
- For every finding, identify the attacker-controlled input, the source-to-sink path, the violated invariant or threat scenario, and the maximum realistic impact.
- Treat a suspected finding as sufficiently evidenced only when it has a PoC that satisfies the `Security PoC standards` below.
- Prefer invalidating weak findings over preserving speculative ones.
- If a finding may be a Sequelize vulnerability (a `Library responsibility` or `Shared responsibility` disposition), it and all associated PoCs, regression tests, and technical details must remain private. Report it through the process and disclosure timeline in `SECURITY.md`; never open a public issue or pull request containing them. Findings that only document application misuse or hardening guidance may be raised publicly.

## Security PoC standards

- Write PoCs as regression tests in the package that owns the behavior, using the existing test harness and fixtures where possible.
- Assert the secure behavior, not the vulnerable implementation detail. The test must fail on vulnerable code and pass unchanged after the fix.
- Start from a reachable public API or another trust-boundary endpoint available to the relevant actor. Internal-only helper tests do not prove exploitability.
- Exercise the reported root cause directly with realistic attacker-controlled input and trusted application configuration. Do not substitute a different trigger or tweak inputs only to make the test fail.
- Keep PoCs short, self-contained, and readable. They may use repository-documented test services, including Docker-backed database services, but must not depend on machine-local files or manual machine-specific configuration beyond documented project prerequisites.
- Use the narrowest command that runs the PoC and report that exact command with the real output showing the failing assertion or concrete blocker.
- If no valid reachable PoC can exercise the claimed root cause, report the concrete reason instead of writing a substitute test. Leave finding disposition to the operator reviewing the result.
