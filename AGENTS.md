# AGENTS.md

This file provides guidance to AI coding agents working with this repository.

## Project map

- Sequelize is a Yarn / Lerna monorepo for the ORM core and its dialect packages.
- `packages/core` contains the shared ORM implementation and most cross-dialect tests.
- `packages/{postgres,mysql,mariadb,sqlite3,mssql,db2,ibmi,oracle,snowflake}` contain dialect-specific connectors and behavior.
- `packages/utils`, `packages/validator-js`, and `packages/cli` are separate published packages with their own build and test scripts.
- Edit source under `packages/*/src`; `packages/*/lib` is generated by the build and should not be hand-edited.
- `build-packages.mjs` is the package build entry point; package scripts call it through `yarn build` / `lerna run build`.

## Branching and PRs

- Normal changes target `main`; the contribution guide only calls out `v6` as an exceptional target when agreed with maintainers.
- Bug fixes and new features must include an automated regression test that fails without the change.
- PR titles use the repository's conventional commit scheme: `docs`, `feat`, `fix`, or `meta`.

## Build

- Use a CI-supported Node line: 20, 22, or 24. Prefer Node 24.
- Before installing, verify `node --version`; if it is not 20, 22, or 24, switch to a supported Node runtime before continuing.
- Do not assume newer Node versions work just because package metadata allows `>=24`; install pulls in native connector packages and untested runtimes can fail before the repo code builds.
- Use Yarn commands for dependency and workspace tasks; this repo is configured for Yarn 4 workspaces and patches.
- Run `yarn install --immutable` from the repository root, then `yarn build`.
- A working native addon toolchain is required because install builds packages such as `sqlite3`, `ibm_db`, `odbc`, and `oracledb`.
- On macOS, runtime tests that import `@sequelize/db2-ibmi` require a system `unixODBC` installation that provides `libodbc.2.dylib`.
- If Nx caching behaves unexpectedly, run `yarn nx reset`.

## Test

- The broad local checks are `yarn test:format`, `yarn test-typings`, and `yarn test-unit`.
- `yarn test-unit` starts with `test/esm-named-exports.test.js`, which imports every published package; missing native connector libraries can fail the suite before assertions run.
- The core test bootstrap in `packages/core/test/config/config.ts` imports every dialect package, so even SQLite-scoped core tests still need the runtime dependencies required by those imports.
- The documented baseline is `yarn lerna run test-sqlite3`.
- The lightest database-backed path is SQLite: `yarn lerna run test-integration-sqlite3 --scope=@sequelize/core`.
- For a single dialect, use the existing package scripts such as `yarn lerna run test-unit-postgres --scope=@sequelize/core` or `yarn lerna run test-integration-postgres --scope=@sequelize/core`.
- Non-SQLite integration tests require the corresponding database service; the repository provides `yarn start-*-oldest` and `yarn start-*-latest` helpers backed by Docker.
- `yarn sscce-sqlite3` is the quickest end-to-end smoke path after build and install.

## Testing and change discipline

- Keep regression tests in the package that owns the behavior: `packages/core/test` for ORM behavior, package-local tests for dialect or utility behavior.
- Use unit tests for pure logic and integration tests when the behavior depends on actual database semantics.
- When public exports change, run the package export checks or `yarn sync-exports` before assuming the build is complete.
- If a test command fails during setup, distinguish missing local prerequisites from code failures before changing source.

## Documentation and threat model

- Update documentation when a public API or user-visible behavior changes.
- `THREAT_MODEL.md` is a living security document; update it when a security-relevant trust boundary, documented invariant, or security-relevant default materially changes.

## Security analysis

- Read `THREAT_MODEL.md` before triaging or escalating any suspected vulnerability.
- Do not treat unusual behavior as a security issue unless you can identify a concrete attacker-controlled input, a reachable code path, and a plausible impact.
- Separate disposition from severity. Use the threat model's categories (`Library responsibility`, `Shared responsibility`, `Defense in depth`, `Out of scope`) independently from impact level.
- Before reporting a finding, check whether it is already covered by an existing issue, advisory, or documented behavior.
- For every finding, identify the attacker-controlled input, the source-to-sink path, the violated invariant or threat scenario, and the maximum realistic impact.
- A finding is ready to submit only after it has a PoC that satisfies the `Security PoC standards` below.
- Prefer invalidating weak findings over preserving speculative ones.

## Security PoC standards

- Write PoCs as regression tests in the package that owns the behavior, using the existing test harness and fixtures where possible.
- Assert the secure behavior, not the vulnerable implementation detail. The test must fail on vulnerable code and pass unchanged after the fix.
- Start from a reachable public API or another trust-boundary endpoint available to the relevant actor. Internal-only helper tests do not prove exploitability.
- Exercise the reported root cause directly with realistic attacker-controlled input and trusted application configuration. Do not substitute a different trigger or tweak inputs only to make the test fail.
- Keep PoCs short, self-contained, and readable. They must not require extra files outside the repository checkout, host-specific setup, or unrelated explanatory commentary.
- Use the narrowest command that runs the PoC and report that exact command with the real output showing the failing assertion or concrete blocker.
- If no valid reachable PoC can exercise the claimed root cause, report the concrete reason instead of writing a substitute test. Leave finding disposition to the operator reviewing the result.
